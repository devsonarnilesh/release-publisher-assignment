# Release Publisher Assessment

## Objective

Implement the release publisher located at:

`/app/publisher/release-publisher.mjs`

The publisher imports a firmware build manifest into DuckDB, reconciles duplicate and withdrawn records using SQL, creates canonical release descriptors, signs each descriptor with the current OpenSSL signing key, submits the signed descriptors to the provided Distribution Gateway, stores publication receipts in DuckDB, and emits deterministic status lines.

The implementation must satisfy all verifier tests without modifying any files outside the publisher implementation.

---

# Files

The publisher must use the following files and paths.

Input manifest:

`/app/fixtures/build_manifest.csv`

DuckDB database:

`/app/releases.duckdb`

Expected report:

`/app/reports/publications.expected.txt`

Current signing certificate:

`/app/keys/current/current.cert.pem`

Current signing private key:

`/app/keys/current/current.key.pem`

Distribution Gateway:

`http://127.0.0.1:7070`

---

# Database Requirements

The publisher is responsible for creating the required tables if they do not already exist.

The database must contain at least the following tables:

* `build_manifest`
* `publications`

The build manifest CSV must be imported into the `build_manifest` table before any reconciliation or publication logic is performed.

The `publications` table must persist successful publication receipts together with the associated request token.

---

# Manifest Reconciliation Rules

The publisher must derive the set of publishable bundles entirely from the imported manifest.

The reconciliation rules are:

1. Remove only **exact duplicate rows**. A duplicate is a row whose values are identical across every column. Rows sharing the same `entry_id` but differing in any other field are **not** duplicates.

2. A `WITHDRAWAL` record references a previous `BUILD` record through the `supersedes_id` column. Any `BUILD` row whose `entry_id` appears in a withdrawal's `supersedes_id` must not be published.

3. Only surviving `BUILD` rows are eligible for publication.

4. Surviving rows must be grouped by `bundle_id`.

For each bundle, compute:

* `artifact_count`
* `total_bytes`

These values become part of the published descriptor.

---

# Descriptor Format

Each publishable bundle must produce one release descriptor.

The descriptor must contain:

* `bundle_id`
* `artifact_count`
* `total_bytes`

The descriptor must be serialized as:

* UTF-8 encoded JSON
* lexicographically sorted object keys
* no insignificant whitespace

All signatures must be generated over these canonical bytes.

---

# Signing Requirements

Before publishing any bundle, obtain the current signing metadata from:

`GET http://127.0.0.1:7070/v1/signing-key/current`

Each descriptor must then be signed using OpenSSL CMS with:

Certificate:

`/app/keys/current/current.cert.pem`

Private key:

`/app/keys/current/current.key.pem`

The signature must be:

* CMS
* detached
* binary
* PEM encoded

Descriptors signed with any revoked key will be rejected by the gateway.

---

# Publication

Publish every signed descriptor to:

`POST http://127.0.0.1:7070/v1/publications`

Each request must include a deterministic request token so that repeated executions of the publisher are idempotent.

For every successful publication, store the returned:

* publication ID
* request token
* publication status

inside the `publications` table.

---

# Output Requirements

Running

```bash
npm run report
```

must emit deterministic status lines for every publishable bundle.

Publication receipt identifiers generated by the gateway are non-deterministic and may vary between executions. The verifier masks receipt identifiers before comparing output.

Apart from receipt identifiers, the output must match:

`/app/reports/publications.expected.txt`

exactly.

---

# Restrictions

The implementation must **not**:

* modify the Distribution Gateway implementation
* read or modify the gateway's internal ledger directly
* bypass CMS signature verification
* hard-code the expected report
* hard-code publication counts
* modify any verifier files

The publisher must derive all publishable bundles from the manifest and communicate with the gateway only through its documented HTTP endpoints.

---

# Success Criteria

A correct implementation satisfies all of the following:

* `npm run report` completes successfully.
* The generated report matches `/app/reports/publications.expected.txt` (after receipt masking).
* DuckDB contains the imported manifest and persisted publication records.
* Re-running the publisher produces identical output and does not create duplicate publications.
* All tests in `/tests/test.sh` pass, causing `/logs/verifier/reward.txt` to contain `1`.
